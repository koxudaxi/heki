## What it does
Reports each group of the project's modules that import each other while they load. A group is
a set of modules each of which reaches every other one through imports in module bodies: an
import cycle, or several cycles sharing modules. Each group is reported once, at the import that
closes a shortest cycle from the group's first module by name, with the other imports of that
cycle as related locations.

The imports that count are those of the timing classes `[tool.heki.imports] cycle-edges` names,
by default only `"body"`:

- `"body"`: an import that runs while its module loads. It is in the module body or in a class
  body the module body runs, also on a branch or inside `try`. A constant by-name import there
  (`importlib.import_module("pkg.b")`) counts too, and so does a lazy import (`lazy import`, or a
  name `__lazy_modules__` lists) whose name the module body reads.
- `"lazy"`: a lazy import whose name the module body does not read.
- `"function"`: an import inside a function.
- `"type-checking"`: an import under `if TYPE_CHECKING:`, which never runs.

What an import loads is decided as Python decides it, as for `IMP201`: `from pkg import name`
imports the submodule `pkg.name` only when `pkg/__init__.py` binds no `name` before importing
it. An import also loads the parent packages of its module first: `import pkg.sub.leaf` runs
`pkg/sub/__init__.py`, and that load is a step of a cycle. The packages holding the importing
module are the exception: Python loaded them before the module ran, so `import pkg.b` in
`pkg/a.py` does not step back into `pkg/__init__.py`. An import of such a package itself, or of
a name it binds (`from pkg import name` in `pkg/a.py`), is a step: it reads the package while it
may still be loading. A name the package binds nowhere, with no module of that name among the
project's files, is a submodule Python finds elsewhere (a compiled extension module), and no
step.

## What a report states

A report states that the modules of the group import each other: each step of the cycle it
shows is an import, of a class `cycle-edges` names, written in one module and loading the next
module or, first, its package.

Its premises:

- **Timing class**: each import is of a class `cycle-edges` names. An import whose class heki
  cannot tell (a lazy import whose reads heki cannot place) is no step.
- **Module loaded**: each import loads that project module: the name it gives, made absolute and
  resolved against the project's modules, with `from` imports split between a submodule and an
  attribute as for `IMP201`. An import whose module heki cannot name is no step: a by-name import
  of a name the code does not fix, or `from a import c` where heki cannot tell whether `c` is the
  submodule `a.c` (the package `a` loads either way, and is a step unless it holds the importing
  module, which then may not read it).

A report says where each import of the cycle is written, never that a branch around it is
taken, and never that the cycle fails: modules that import each other can load fine.

## Why is this bad?
Modules that import each other while they load work only while their statements stay in an
order that lets each one find what it needs: moving a definition, adding an import, or importing
another module of the group first can make an import fail with an `ImportError` about a
partially initialized module. A group of modules importing each other also cannot be loaded,
tested, or understood one at a time. Unlike a check that reads only the import statements, heki
counts the imports that run while modules load: imports inside functions and under
`TYPE_CHECKING` count only when `cycle-edges` asks for them, and it knows which module `from a
import b` loads.

## Example
```python
# pkg/a.py
from pkg.b import helper_b


def helper_a() -> int:
    return helper_b() + 1
```

```python
# pkg/b.py
from pkg.a import helper_a  # IMP101: closes the import cycle `pkg.a` -> `pkg.b` -> `pkg.a`


def helper_b() -> int:
    return 1


def uses_a() -> int:
    return helper_a()
```

Use instead:
```python
# pkg/b.py
def helper_b() -> int:
    return 1


def uses_a() -> int:
    from pkg.a import helper_a

    return helper_a()
```

## How to fix
When one import is on every cycle of the group, the help names it: moved into the functions that
use it, or made `lazy` on Python 3.15 and later, it leaves the group's modules with no cycle.
heki names it only after one search of the group's other imports finds no cycle without it, and
offers only a change that takes it out of the classes `cycle-edges` counts: no move into a
function when `"function"` counts, and no `lazy` when `"lazy"` counts, before Python 3.15, or
where Python rejects the keyword (a class body, a `try` statement). Of several such imports it
names the one closing the reported cycle, else the first on it. It names no import whose name
code running while its module loads may read: the module body with its class bodies,
decorators, defaults, bases, and the annotations the target version evaluates in place, the
module's functions these call or apply as decorators, and its `__all__`, which a star import of
the module reads. Moved into a function, such an import leaves that read unbound, and made
`lazy`, it loads at the read, still while its module loads. Nor does it name one whose name
another project module takes while that module loads: by `from m import name`, a star import
of the module (for a public name), or an attribute read off the module object (`import m`,
then `m.name`), also through a package that re-exports the name, unless the module rebinds the
name later, so that other modules never see the import's binding. Moved, the import leaves the
module without the name, so the move is offered only while no other module reads it at all; a
read in a function leaves `lazy`, which loads at that read. An import in a class body binds a
class attribute, which heki does not follow, so it is never named. Without such an import, the
help lists the general ways out.

## Fix safety
No automatic fix.

## Options
- `[tool.heki.imports]`: `cycle-edges`, the timing classes of the imports that count
  ([configuration](../configuration.md#imports-toolhekiimports)).
- Its reports are heuristic warnings: `lint.fail-on = "warning"` makes a cycle fail the run.
- A [Ratchet baseline](../adoption.md#import-cycle-groups) records each group by its modules,
  not by the import its report sits at: an entry covers a group when it holds all of the
  group's modules.

## Known limitations
- Imports heki does not see (`exec`, `runpy`, a module loaded from a file path, a write to
  `sys.modules`) are no steps, and neither is a cycle through a module outside the project.
