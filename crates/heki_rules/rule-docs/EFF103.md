## What it does
Checks loops that run a database query on every iteration (the "N+1 queries" problem):
`cursor.execute(...)`, `session.execute(...)` (awaited ones on async sessions and connections
too), the Django `QuerySet` methods that run the query (`get`, `first`, `count`, ... and their
`a*` variants), `pymongo`, `redis`, and DynamoDB commands, `pandas.read_sql`, and project
functions that reach them, including the getter of a property read in the loop and a generator
iterated in the loop (its body runs where it is iterated, as for `EFF101`).

It does not report reading the rows of a statement already executed (`cursor.fetchone()`),
calls that only build a query (`QuerySet.filter(...)`, `Redis.pipeline()`), DDL statements
(`CREATE`, `ALTER`, `DROP`, `PRAGMA`), migration code (`upgrade` / `downgrade` functions, files
under `migrations/` or `alembic/`), the ORM packages' own implementation, or loops whose size the
code fixes when no data-sized loop is around them (`for ident in enumerate((1, 2), 1)`,
`zip(order, ["m1", "m2"])`, a name bound to a small display; see `EFF102`).

## Why is this bad?
One round trip per item makes the run time grow with the number of rows and with the network
latency to the database. A single batched query is usually orders of magnitude faster.

## Example
```python
def names(cursor, ids: list[int]) -> list[str]:
    out = []
    for i in ids:
        cursor.execute("SELECT name FROM users WHERE id = ?", (i,))  # EFF103
        out.append(cursor.fetchone()[0])
    return out
```

Use instead:
```python
def names(cursor, ids: list[int]) -> list[str]:
    marks = ",".join("?" * len(ids))
    cursor.execute(f"SELECT name FROM users WHERE id IN ({marks})", ids)
    return [row[0] for row in cursor.fetchall()]
```
